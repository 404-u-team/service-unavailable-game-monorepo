## О проекте

REST API (fastapi) на Python с:

* PostgreSQL (asyncpg)
* Kafka 
* WebSocket
* Docker / Docker Compose

Основная задача — поддерживаемый backend без лишних абстракций и усложнений.

---

## Архитектура

Основной поток REST-запроса:

```
Router → Handler → Service → Repository → PostgreSQL
```

Kafka:

```
Producer → Kafka → Consumer → Service
```

WebSocket отвечает только за транспорт и управление соединениями. Бизнес-логика должна находиться в сервисном слое.

### Ответственность слоёв

**Router**

* маршруты;
* зависимости;
* middleware.

**Handler**

* HTTP/WebSocket взаимодействие;
* получение и валидация входных данных;
* вызов сервисов;
* формирование ответа.

**Service**

* бизнес-логика;
* бизнес-правила;
* координация нескольких компонентов.

**Repository**

* работа с PostgreSQL;
* запросы и операции с БД.

Handler не должен обращаться к Repository напрямую.

Repository не должен содержать бизнес-логику.

## Общие правила

* Перед изменением кода изучить существующую реализацию и связанные с задачей файлы.
* Сначала использовать существующие решения и абстракции, если они подходят.
* Не создавать новые абстракции без необходимости.
* Не добавлять зависимости без явной причины.
* Не изменять код, не связанный с текущей задачей.
* Не делать большой рефакторинг в рамках небольшой задачи.
* Сохранять существующие соглашения проекта.
* Использовать type hints.
* Предпочитать простой и читаемый код.
* Не дублировать существующую функциональность.

## Асинхронность

Проект использует async I/O.

Не использовать блокирующие операции внутри async-кода.

Для сетевого взаимодействия, PostgreSQL, Kafka и WebSocket использовать асинхронные API, если они доступны и используются в проекте.

Не добавлять `async` функциям, которым асинхронность не нужна.

---

## PostgreSQL

Вся работа с БД должна проходить через Repository или специально выделенный database layer.

На момент разработки будет один файл миграции. При нужде изменении модели БД меняется этот один файл вместо создания новых файлов миграции.

Работа с БД осуществляется через SQL запросы только, без ORM

При изменении моделей БД проверить необходимость:

* новой миграции;
* изменения индексов;
* изменения ограничений;
* обновления тестов.

Не изменять уже применённые миграции без необходимости.

Если несколько операций должны выполняться атомарно, использовать одну транзакцию.

---

## Kafka

Kafka используется для асинхронного взаимодействия и событий.

Схемы событий должны быть явными и стабильными.

Consumer должен корректно обрабатывать повторную доставку сообщений. По возможности обработка событий должна быть идемпотентной.

Не подтверждать сообщение до успешного завершения необходимой обработки.

Ошибки обработки сообщений не должны приводить к бесконечному retry.

При добавлении нового Kafka-события проверить:

* producer;
* consumer;
* схему сообщения;
* обработку ошибок;
* идемпотентность;
* тесты.

---

## WebSocket

WebSocket отвечает за:

* установление соединения;
* аутентификацию;
* получение и отправку сообщений;
* управление подключениями;
* отключение клиентов.

Бизнес-логика должна находиться в Service, а не в WebSocket handler.

Всегда корректно обрабатывать отключение клиента.

Если WebSocket используется для доставки Kafka-событий, не связывать consumer напрямую с деталями WebSocket-протокола без необходимости.

---

## API

API-контракты должны быть явными.

При изменении endpoint необходимо проверить:

* request schema;
* response schema;
* ошибки;
* связанные тесты;
* документацию, если она используется в проекте.

Не менять существующий API-контракт без явного требования задачи.

При внутренних ошибках системы, не зависящих от пользователя, пользователь получает ошибку 500 без особых подробностей произошедшего, а система обязательно логгирует саму ошибку в формате: "Ошибка при получении данных пользователя {user_id!r}: {exception}".
---

## Обработка ошибок

Для ожидаемых ошибок использовать существующий механизм application/domain exceptions проекта.

Не использовать повсеместно:

```
except Exception:
```

Если ошибка неожиданная, не скрывать её.

Не игнорировать исключения без причины.

---

## Конфигурация

Секреты и окружение не должны храниться в исходном коде.

Использовать существующую систему конфигурации проекта.

Не добавлять новые способы конфигурации без необходимости.

---

## Тестирование

При добавлении нетривиальной логики добавлять соответствующие тесты.

Для database/Kafka интеграций по возможности использовать реальные тестовые сервисы, а не полностью мокать инфраструктуру.

При исправлении бага добавлять regression test, если это имеет смысл.

Перед завершением задачи запускать подходящие formatter, linter и tests.

Если какой-либо check невозможно запустить, указать это.

---

## Работа с задачами

Для небольших задач можно сразу переходить к реализации после изучения кода.

Для крупных изменений сначала составить краткий план:

1. какие файлы будут изменены;
2. какие файлы будут добавлены;
3. какие компоненты затронуты;
4. нужны ли изменения БД/API/Kafka/WebSocket;
5. какие тесты потребуются.

После реализации проверить итоговый diff и убедиться, что в него не попали лишние изменения.

---

## Приоритеты

При выборе решения приоритет следующий:

1. Существующие соглашения проекта.
2. Простота и читаемость.
3. Корректность.
4. Тестируемость.
5. Производительность, если она действительно важна для конкретной задачи.

Не использовать сложные архитектурные паттерны только потому, что они существуют.

Не добавлять CQRS, event sourcing, дополнительные очереди, кэширование, микросервисы или другие архитектурные усложнения без конкретной необходимости.
